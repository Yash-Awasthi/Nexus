# Evaluations

Claims about retrieval and entity merging are worth what their labels are worth. This page records the
measurements behind those claims, generated from the committed labelled set so the numbers cannot be
remembered differently from what the code does.

## What is measured, and with what

- **Corpus.** Three knowledge bases — an operations runbook set, a billing policy set and an access
  policy set — twelve documents each, with deliberate near-misses (two documents about the same
  subsystem) so topic-only matching ranks wrongly. Labels live in
  [`packages/search/src/eval/dataset.ts`](../packages/search/src/eval/dataset.ts).
- **Queries.** Fifty, written the way a person asks (a paraphrase, a pronoun, a number in words), each
  naming the document that answers it and every document that would be acceptable. A set that reuses a
  document's own keywords measures memory, not retrieval.
- **Retrieval.** The shipped code: `InMemoryBM25`, `rrfFusion` / `weightedAlphaFusion` through
  `HybridSearchEngine`, and `BM25Reranker`.
- **Embedder.** A deterministic hashed bag-of-words-and-bigrams with 256 dimensions
  ([`metrics.ts`](../packages/search/src/eval/metrics.ts)). It is deliberately weak: it sees shared
  vocabulary, not meaning. The numbers are therefore a _floor_ for the retrieval stack, and they are the
  same on every machine, which is what makes them a gate. A model-backed embedder can only improve on
  them.
- **Metrics.** Recall@1 and Recall@5 over the acceptable set, MRR of the first acceptable document, and
  citation accuracy (the first result is the document that answers the question).

`pnpm evals` regenerates the block below; `pnpm evals:check` fails when it drifts, and
`packages/search/tests/eval/retrieval-quality.test.ts` gates the floors.

### Ablation

Same queries, same embedder, only fusion/weights/rerank changed. Citation accuracy decides; MRR breaks ties.

| Configuration              | n   | Recall@1 | Recall@5 | MRR   | Citation accuracy |
| -------------------------- | --- | -------- | -------- | ----- | ----------------- |
| rrf 0.5/0.5 (default)      | 50  | 54.0%    | 86.0%    | 72.4% | 54.0%             |
| rrf 0.5/0.5 + rerank       | 50  | 59.0%    | 86.0%    | 78.2% | 62.0%             |
| rrf 0.7 dense / 0.3 sparse | 50  | 49.0%    | 83.0%    | 67.8% | 48.0%             |
| rrf 0.3 dense / 0.7 sparse | 50  | 60.0%    | 84.0%    | 78.0% | 60.0%             |
| alpha 0.5                  | 50  | 60.0%    | 87.0%    | 78.0% | 58.0%             |
| alpha 0.7                  | 50  | 56.0%    | 86.0%    | 75.2% | 56.0%             |
| alpha 0.3                  | 50  | 60.0%    | 86.0%    | 77.9% | 62.0%             |
| alpha 0.7 + rerank         | 50  | 59.0%    | 86.0%    | 78.2% | 62.0%             |

The winner is **rrf 0.5/0.5 + rerank** (citation 62.0%, MRR 78.2%). The shipped default keeps RRF 0.5/0.5 without a reranker: reranking wins five queries and loses one on citation (a one-sided sign test over six discordant queries gives p = 0.11), which is not enough evidence to change a default for every caller, and the one route that already reranks (`/researcher`) keeps doing so.

### Chunking

The shipped chunker at each strategy over the same documents and queries, scored at document level (chunks inherit their source document).

| Strategy  | Chunks | Mean chunk (tokens) | Recall@1 | Recall@5 | MRR   |
| --------- | ------ | ------------------- | -------- | -------- | ----- |
| fixed     | 55     | 69                  | 34.0%    | 60.0%    | 47.3% |
| sentence  | 36     | 97                  | 34.0%    | 64.0%    | 48.6% |
| paragraph | 36     | 97                  | 34.0%    | 64.0%    | 48.6% |
| semantic  | 114    | 31                  | 26.0%    | 62.0%    | 43.2% |

**Recommendation:** index whole documents while they are short. Chunking every document costs more than it gains here — the best chunked strategy reaches 64.0% Recall@5 against 86.0% for whole documents — and `semantic` produces three times as many chunks for the worst Recall@1. Chunk when a document is longer than a model's useful context, and prefer `paragraph` (identical to `sentence` on this corpus, fewer fragments than `fixed`).

### Entity merge quality

Hashing `name|type` over 18 labelled pairs: precision 100.0% (0 false positives), recall 88.9% (1 false negative). The hashing rule normalises NFKC, case, whitespace runs and trailing punctuation; it does not know synonyms, which is why `St. Louis` and `Saint Louis` stay two nodes. A false positive would fuse two different entities silently — none in this set.

## Limitations, stated rather than implied

- Fifty queries is enough to catch a collapse and not enough to settle a two-point difference. The
  ablation section says which comparisons are inside the noise instead of calling a winner.
- The corpus is short documents. A finding like "chunking loses recall" is true here and is exactly why
  the recommendation is to chunk only when a document is longer than a useful context, not as a default.
- Entity extraction itself is model-backed in production and is not measured here; what is measured is
  the deterministic identity rule the graph uses to decide two mentions are one node.
