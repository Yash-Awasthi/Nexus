# SLO review — 2026 Q4 (baseline)

The first review on record. It is a **baseline, not a verdict**: there is no production traffic in this
quarter, so every budget is untouched and the interesting content is the measurement method and the two
drifts the review found before any traffic could hide them.

## Quarter

2026-10-01 → 2026-12-31. Reviewed 2026-11-25. Reviewer: the maintainer of record (`docs/ONCALL.md` §1 —
the rotation is one person, so there is no second reviewer to name).

## Actions taken

None were required: no budget is exhausted, and inventing an action for an empty quarter would be
theatre.

Two drifts were found by measuring instead of asserting, and both are fixed:

1. **The tracker was stricter than the promise.** `SloTracker` was configured for 99.9% availability
   and a 0.1% error rate while `docs/slos.md` promises 99.5% and 0.5%. `budgetRemaining` therefore
   reached zero at a fifth of the error the promise allows — an operator would have been told the
   budget was gone with four fifths of it left. Now 0.995 / 0.005 in `apps/api/src/routes/metrics.ts`.
2. **The latency target was four times looser than the documented one.** The tracker flagged a
   violation at 2 000 ms while SLO-2 says p99 < 500 ms; the alert would have stayed silent through a
   4× breach. Now 500 ms, and `scripts/slo-review.mjs --check` compares all three numbers against
   `docs/slos.md` so they cannot drift again.

## Changes for next quarter

- **SLO-3 and SLO-4 need a real SLI before the next review.** Both are currently "not instrumented in
  production", which is an honest answer in a baseline and an unacceptable one in a real quarter. Plan:
  record council deliberation outcomes at the route that returns them, and worker job latency at the
  queue's completion hook.
- **The review stays quarterly, with the decision policy fixed.** `docs/slo-reviews/README.md` holds the
  table that says what happens when a budget is gone, so the next review applies a policy instead of
  negotiating one.
- **No SLO targets move this quarter.** Moving a target to make a report look better is the failure
  mode this record exists to prevent.

## Evidence

```bash
node scripts/load-probe.ts                     # p99 for the API's own routes (local floor)
node scripts/slo-review.mjs --check            # targets in docs/slos.md vs the tracker vs this record
curl -s localhost:3100/api/v1/metrics | grep nexus_slo_   # the live series, when there is traffic
curl -s localhost:3100/status                              # the five dependency probes
```

The `--check` gate is the part that keeps this page true: it fails when `docs/slos.md`, the tracker's
configured targets and the table above disagree, in either direction.
