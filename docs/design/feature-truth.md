## 2. Corrections to Part 1 of the enhancement plan

Four numbers in the plan do not survive a direct count. They are recorded here so later stages size
their work from the real figures.

1. **`routes.ts` registers 116 entries, not 117.** The file holds 114 `route(...)` calls, one
   `index(...)` and one `layout(...)`. The layout, `routes/marketing-layout.tsx`, contributes no
   path of its own, so there are 115 addressable paths.
2. **The sidebar lists 52 items, not roughly 55.** Counted from the `navGroups` array in
   `apps/ui/app/root.tsx`; every `to:` value resolves to a real route entry, so the sidebar has no
   broken links.
3. **This scan finds 851 endpoint registrations, against the 872 the plan records.** The scan is
   a regex over `app.<method>(...)` calls, so it is a lower bound: registrations built through a
   helper or a loop are not counted. Treat 851 as the floor, not a contradiction.
4. **A dedicated handler file is not automatically durable.** The §16.7 extraction moved several
   surfaces out of `api-bridge.ts` into their own files without changing how they store data. Four
   of them still hold state in process memory and lose it on restart:

   | File                        | State                                                                                      |
   | --------------------------- | ------------------------------------------------------------------------------------------ |
   | `routes/rooms.ts`           | `_roomsStore`, a module-level `Map`. Its own header says the store "moves here unchanged". |
   | `routes/sandbox.ts`         | `_sandboxResults`, a capped module-level `Map`.                                            |
   | `routes/conductor-route.ts` | `_jobLog`, a module-level array truncated to the last 200 entries.                         |
   | `routes/connectors.ts`      | `enabledOverrides`, `oauthStates` and `credentialVault`, all module-level `Map`s.          |

   The Stage B3 exit criterion — "every `product` row is backed by a durable handler" — is not met
   by moving a handler out of the bridge alone. The **Backing** column below states the storage each
   handler actually uses, so a later stage can tell the two apart.

## 3. How to read the table

**Sidebar** — whether the path appears in `navGroups` in `apps/ui/app/root.tsx`.

**Endpoints** — every API path the route reaches, including paths reached through
`app/lib/deliberate.ts`, `app/lib/council.ts` and the components the route renders. Endpoints are
attributed by imported symbol, not by imported module, so a page that imports only
`loadCouncilMembers` (a `localStorage` read) is not credited with the network call that
`syncCouncilFromServer` makes. `:x` stands for an interpolated path parameter.

**Backing** — the storage each handler uses, read out of the handler source.

**Class** — one of three values:

- `product` — a real user-facing capability with a durable handler behind it.
- `experiment` — it works, but it is a research toy or a one-off demo, whatever the handler quality.
- `dead` — the page calls nothing, calls an endpoint that does not exist, or renders placeholder
  data.

The line between `product` and `experiment` is a judgement call, so the rule applied here is stated
explicitly: **a row is `experiment` if it demonstrates a deliberation or LLM research technique and
is not on the path a user takes to run a deliberation, or to manage its knowledge, its cost, or
their account.** Every `experiment` row can be moved by disagreeing with that one sentence rather
than by re-deriving the table.

**Promote** — set on `product` rows whose capability is served by synthetic storage today: the
legacy bridge, or one of the four dedicated-but-in-memory handlers from section 2. This column is
the Stage B3 work list.

**One documented exception to the "every `product` row names a durable handler" rule.** Fourteen
rows are static marketing or client-only pages — the landing page, pricing, about, careers, the
eight `/product/*` pages, the layout wrapper, and the infrastructure calculator. They call no
endpoint by design and their Handler column reads `—`. Calling them `dead` would be literally
correct under the definition and useless in practice, so they are `product` with an empty handler.
No other row uses this exception.

**Shell-level calls are excluded from every row.** `AuthContext` (`/api/v1/auth/login`,
`/api/v1/auth/refresh`) and `NotificationsContext` (six `/api/notifications*` paths) wrap every
authenticated page. Listing them 100 times would bury the per-page signal. `auth-users.ts` is
Postgres-backed and `notifications.ts` is backed by `lib/notifications-store.ts`; both are durable.

## 8. Cross-cutting findings, recorded and not fixed

Stage A is read-only. Each of these was observed during the pass and left in place.

1. **The product is called JUDICA in sixteen UI files.** `blog.tsx`, `careers.tsx`, `chat.tsx`,
   `contact.tsx`, `infra-calculator.tsx`, `landing.tsx`, `llm-leaderboard.tsx`, `pricing.tsx` and
   all eight `product.*.tsx` pages use the old name in user-visible copy. Section 6.6 of the
   enhancement plan settles that this ships as a standalone product, so the name it ships under has
   to be settled with it. Stage C2 is the natural home.
2. **`routes/connectors.ts` keeps connector credentials in a module-level `Map`.** `credentialVault`
   at line 218, alongside `oauthStates` at line 151. Credentials are lost on restart and shared
   across the process. This is the same class of gap that section 6.4 Tier 1 assigns to the secret
   store, and it is a present issue rather than a missing feature.
3. **`streamCouncilDeliberation` in `app/lib/api.ts` has no callers.** It is the only client helper
   that drives `/api/v1/council/deliberate/stream`, the durable council path from finding 1.4. No
   route or component imports it; the pages that import from `app/lib/api.ts` take only `authFetch`.
   The durable council is wired on the server, has a client, and is reached by nothing.
4. **`/pricing` has no call to action.** Ninety lines, no `href` and no `onClick` anywhere in the
   file. The pricing page cannot convert a visitor into a signup.
5. **`routes/repos.ts` documents its own dead branch.** Its header records that the tree-fallback in
   `/repos/:id/search` is unreachable either way, and names itself a follow-up cleanup candidate.
   Kept as-is.
6. **`/setup` and `/god-mode` persist council membership to `localStorage` only.** Both import from
   `app/lib/council.ts` without importing `syncCouncilFromServer`, so the council a user configures
   at first launch never reaches the server and does not follow them to another browser.
