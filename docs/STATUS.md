**How to test the AI quickly:** register in the UI, then any LLM page works locally. Or curl:

```bash
API=http://localhost:3000
T=$(curl -s -X POST $API/api/v1/auth/register -H 'Content-Type: application/json' \

curl -s -X POST $API/api/reasoning/run -H "Authorization: Bearer $T" \
  -H 'Content-Type: application/json' -d '{"question":"hi"}'
```

## Architecture — durable research jobs (recorded 2026-09-06, pass 4)

Research jobs were the last in-memory store feeding user surfaces: after any API restart, dashboard rows, the research history sidebar, and every `/deep-research?id=…` deep link (dashboard rows + notification links) 404'd — the notification said "report ready" but the record behind it was gone.

- **`lib/research-jobs.ts`** mirrors threads-store/notifications-store: `research:list:{uid}` id index (newest first) + `research:item:{uid}:{id}` records, 90-day TTL (outlives the 30-day notification linking to it), 200-job cap, per-key mutation lock (shared `lib/with-key-lock.ts`, extracted from threads-store — now two consumers). Records carry: id, query, status, `createdAt`/`updatedAt`, report + result alias, sources, citations, relatedQuestions, cycles, durationMs, stats (`{requests, tokens}` from the synthesis usage), error.
- **api-bridge delegates, gains nothing**: `_researchJobs` (Map + all 7 uses) deleted; `GET/POST /api/research`, `GET /api/research/:id`, and the dashboard aggregate read/write the store. The stream handler write-throughs on start (status touch), done (full record), and failed (error message); related questions are generated fire-and-forget after completion (bounded by the existing timeout, never slows the stream) and written back. All research routes now resolve the caller via `requireAuthWithTier` — jobs are per-user, consistent with notifications/threads, which also fixes the previous cross-user visibility of every job.
- **Engine untouched**: `WebResearcher`, the search/synthesize functions, `withTimeout`, and the Tavily `AbortSignal` guard are exactly as before — only the persistence points changed.
- The shared per-key lock moved to `lib/with-key-lock.ts` (threads-store + research-jobs import it; threads-store tests still cover the race it prevents).

Verified live (the decisive proof): ran a research job to completion through the real UI (18 s, Tavily + LLM) → record persisted with report (1745 chars), 6 sources, 6 citations, 5 related questions, stats `{requests: 1, tokens: 2131}` → **restarted the API** (tsx watch, new PID, all process state wiped) → `GET /api/research/:id` returned the intact record → a fresh `/deep-research?id=…` page rendered the full report from the persisted record, and the dashboard research card showed the job. 68 unit tests green (8 new for the store), api typecheck 0 errors.

Rules later passes should keep:

- Research routes resolve the caller with `requireAuthWithTier` and read/write only through `lib/research-jobs.ts` — never reintroduce process-level research state in api-bridge.
- Write-through updates go through `updateResearchJob` (locked, best-effort, bumps `updatedAt`); completion must persist BEFORE the done SSE event and notification so a subscriber that follows the link can never race an empty record.
- `listResearchJobs` returns newest-first by list position (timestamps can tie) — do not sort by `createdAt` alone.

Rules later passes should keep:

- **Never re-add the notification tray to `/api/dashboard`** — the tray is owned by the store + `NotificationsContext`; the aggregate carries stats/series/research only. A badge that read the aggregate could disagree with the bell (the bug this split fixes).
- **Never add `/api/notifications*` handlers inside `api-bridge.ts`** — they live in `routes/notifications.ts`; duplicating them there throws `FST_ERR_DUPLICATED_ROUTE` at boot.
- `/health/ready` checks are `"ok"`/`"down"` strings — compare `health?.db === "ok"`, never `.ok`.
- `listNotifications` counts unread over the whole tray (bounded ≤200), then slices — the `unreadCount` field is always the true count.
- **Live delivery**: every creator must go through `createNotification()` (the store) — it publishes the SSE event; bypassing it (writing KV directly) silently silences the stream. The UI consumes SSE via `fetch`+reader with the bearer header, never `EventSource`.
- The client keeps the 60 s count poll as a safety net for other tabs/agents; the stream is the fast path, the poll is the reconciler.
- **Weekly digest**: fires on the FIRST `/api/dashboard` load of a new week and reports the previous completed Mon–Sun week — activity created today is reported by the first load after the next Monday, never mid-week. The week marker is written BEFORE stats compute, so repeated loads can never double-emit and quiet weeks are marked silently. Digest stats are workspace-wide (cost log / research / autopilot are not per-user); the notification itself is per-user — correct for single-workspace installs.

## Architecture — rate-limit window-drain fix (recorded 2026-09-06, pass 10)

Fix for the demonstrated never-draining-bucket wedge in `lib/rate-limiter.ts`: `ratelimit:api:127.0.0.1` had sat at 385 > 300 with every request 429ing forever. Root cause: the fixed-window counter refreshed its expiry on **every** request — the Upstash pipeline ran unconditional `INCR`+`EXPIRE`, and the KV fallback's plain `SET` clears (Redis) or re-stamps (memory) the TTL — so once over the limit, the bucket never reset while any traffic (e.g. the notifications SSE reconnect loop) kept touching the key.

- **Upstash path** (`_atomicIncrWithTTL`): the pipeline now sends `INCR` alone; `EXPIRE` is issued **only when `INCR` returns 1** (this call created the key). The atomic pipeline design is unchanged — no read-modify-write. A failed EXPIRE is tolerated (one key without a TTL) rather than double-counting through the fallback.
- **KV fallback** (`_getCurrentCount`): the count key carries no TTL; a separate window marker (`<key>:w`) is stamped with the TTL exactly once at the first request of the window, so in-window writes can never refresh the expiry — the bucket drains at the window boundary even under continuous traffic.
- **Concurrency** (found by the live proof): the marker check + count write is check-then-act; 320 simultaneous arrivals all saw the missing marker and stampede-reset the count to 1 (zero 429s). Per-key promise-tail serialization (`_serializedCount`) restores the single-process atomicity the fallback documents; the Upstash INCR path was already atomic.

Regression tests (4 new, `tests/lib/rate-limiter.atomic.test.ts`): EXPIRE appears only on key creation (Upstash bodies asserted); a bucket pushed over the limit drains after the window when traffic stops; in-window traffic does not refresh the expiry (clock-injected MemoryKVStore); 100 concurrent arrivals on a limit-10 bucket produce exactly 90 429s and a final count of 100.

Verified: rate-limiter suite 26/26, full lib tier **189/189**, api + ui + worker typechecks 0 errors, prettier clean. Live proof through the real server (fake-IP key via `X-Forwarded-For`, no Redis keys cleared): 320 concurrent requests → exactly 300×200 then 20×429 from request 301, Redis count byte-exact 320 with the marker TTL stamped once; a mid-window probe → 429 while the marker TTL kept draining (not refreshed); after the 60 s window → 200. - **FailoverDriver** (`lib/llm-failover.ts`): `getDefaultDriver()` now returns a failover driver over the registry in order — `NEXUS_LLM_PROVIDER` first, then the historical default order (openrouter > anthropic > groq > openai > ollama), then extra configured providers (gemini/deepseek/mistral). `complete()` tries each provider in order; a provider error (auth/rate-limit/network) fails over to the next; every response carries `servedBy: <providerId>`. `stream()` fails over only when the previous provider threw BEFORE emitting any delta — partial output is never replayed onto a second provider.
- **Composition with the cache**: FailoverDriver sits OUTSIDE one CachingDriver per provider. The cache key already includes the wrapped driver's provider identity, so entries never cross providers (an entry stored by A is only ever served as A). ## Architecture — final-completion cache for the council/thread stream path (recorded 2026-09-07, pass 16)

The audit's last SPEC gap: council/thread deliberations (`POST /api/chat/stream`, the user's token-reduction ask) handed RAW registry drivers to `stream()` via `driverFor` — the entire delivered cache surface (KV-backed, ALS-per-user, deterministic-only) was bypassed. Now those streams ride the SAME cache, as a **final-completion** cache: only the fully-assembled result of a clean stream is ever stored.

- **Deterministic gate checked first** (honesty constraint): `CachingDriver.stream()` honors the shared gate — temperature > 0, tools/toolChoice, or `tool`-role messages bypass with the skip counter incremented (`streamSkips`), exactly like `complete()`. The council route's actual generation config sends **no temperature** (`{ model, messages, maxTokens }`), so it is deterministic-eligible under the documented gate — the same "temperature unset = provider default" contract the complete() cache already live-proved (byte-identical replays on the same infra). I did NOT force caching onto a non-deterministic config; if the route ever sets temperature > 0 the gate fires and the streams land uncached, observable as `streamSkips`. (The /chat/stream surface exposes no temperature knob, so the gate-fires path is proven in unit tests + the shared complete()-path contract rather than a live council call — stated honestly.)
- **Only clean full streams are stored — never a partial**: the wrapper forwards every delta, and stores ONLY when the inner stream resolved to the end with a `"stop"` finish, no tool calls, and no handler abort. An error, a mid-stream throw (client gone), a tool-call sequence, or a non-stop finish leaves the cache untouched (tested: retry re-streams from the provider every time). A hit replays the stored completion WITHOUT opening a stream — one content delta + done, `cached: true`, ZEROED usage — so the cost log records the replay at $0.
- **Key = provider + model + prompt + caller**, reusing the existing KV-backed tiered store (`llm-cache:<sha256>` over the shared Redis KV) and the ALS caller context (`lib/user-context.ts`); anon bucket for calls outside a request. Per-provider isolation holds because the wrapper is memoized per inner driver (WeakMap) and the key includes the wrapped driver's provider.
- **Council route wired in** (`api-bridge.ts` `/chat/stream`): `driverFor` now returns the memoized `CachingDriver(rawDriver)` instead of the raw driver, and each member's stream result is cost-tracked (`_trackCost`) — real usage on a miss, zeroed on a hit. Council token spend was previously invisible in the cost log; now it is tracked once and replays cost nothing.
- **Observability**: `llmCache` on `/health/ready` gains stream-path counters `streamHits` / `streamMisses` / `streamSkips` plus a `streamServedBy` marker (a hit reports the stored entry's provider; a miss the inner driver's). Complete()-path counters, rules, and bypasses are untouched (the `opts.stream === true` complete()-only rule is preserved — the stream path treats `stream` as a request hint, not a sampling knob). FailoverDriver's stream path (already composed over CachingDriver) picks up the same cache automatically and consistently.
- **Tests**: 8 new in `tests/lib/llm-cache-driver.test.ts` (the old "stream passes through untouched" test was replaced — it asserted the gap this pass closes) — clean full stream cached + replayed byte-identically (zeroed usage, no second inner stream), mutated prompt misses, errored stream never cached, mid-stream abort never cached, tool-call finish never stored, temperature > 0 bypass (skip counter), key isolation across provider + model + caller (u2 never sees u1's deliberation), cross-instance L2 KV hit + `streamServedBy`, stream stats riding `getLlmCacheStats` without touching complete() counters.

## Known caveats

- `_costLog` is durable (lib/cost-log.ts, pass 8) + hardened (pass 9): flush health rides `/health/ready`, and a graceful close flushes the pending tail (bounded 2 s). Best-effort by design: an unclean kill (tsx-watch force-kill on Windows) still loses at most the last few seconds — never the history. A flush straddling midnight whose second day-write fails can double-count that tail on retry (astronomically rare; accepted vs. losing data).
- **Memory cold-recall** can miss once right after restart (Ollama warm-up); warm calls are reliable.
- **Configuration pages** (Language Models, Settings, Profile, Billing, etc.) previously threw `useRef null` from a duplicated React copy → fixed via `resolve.dedupe: ["react","react-dom"]` in `apps/ui/vite.config.ts`.
- `diff/rollback` history (`_diffRollbacks` Map) is same-session-only by design — `rollbackId` lives in React state and is offered right after apply; a restart orphans old ids (no durable edit history). Revisit only if a cross-session rollback UI is ever built.
