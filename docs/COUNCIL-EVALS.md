# Council evaluation

What the council is worth, measured: a golden set of decision prompts, a rubric, a calibrated judge, and the
per-mode and per-archetype numbers that follow from them. The tables are generated by
`pnpm council:evals` and gated by `pnpm council:evals:check` in CI, so this page cannot describe a council
that no longer exists.

Three things this page is **not**:

- It is not a benchmark of any model. The transport is scripted (see below), so the numbers are the same on
  a laptop with no key as in CI. They measure the protocol — how rounds, tallies and costs behave — which is
  the part we can change and regress.
- It is not a release gate for answer quality. The judge's agreement is measured against one annotator's
  labels, which makes it an upper bound; it can rank modes and catch regressions, and it may not certify.
- It is not a leaderboard for archetypes. A win means "top score in its own council", which is a comparison
  among five voices generated by the same driver, not a claim about any real model's persona.

## How the measurement is built

| Piece      | File                                   | What it does                                                                                                                   |
| ---------- | -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| Golden set | `packages/council/src/eval/golden.ts`  | 30 decision prompts with the facts a verdict must engage and the tradeoff it must name; one prompt is unanswerable on purpose. |
| Rubric     | same file                              | Five weighted criteria: coverage 0.30, specificity 0.20, tradeoff 0.20, action 0.20, honesty 0.10.                             |
| Judge      | `packages/council/src/eval/judge.ts`   | Deterministic text scorer plus Cohen's κ against hand labels; refuses to be quoted below κ 0.4.                                |
| Labels     | `packages/council/src/eval/labels.ts`  | 53 hand-labelled verdicts, including fluent-but-empty and numeric-but-one-sided answers.                                       |
| Runner     | `packages/council/src/eval/runner.ts`  | Drives `DeliberationEngine.deliberate` with a scripted transport, three modes, and the cost arithmetic.                        |
| Statistics | `packages/council/src/eval/metrics.ts` | Vote agreement, Wilson intervals, cost per verdict.                                                                            |

### Modes

- **Standard** — one round of five independent votes, 60% of decided votes approves.
- **Red / blue** — two rounds; the second sees the first split.
- **Socratic** — three rounds of re-voting.

### Cost arithmetic

Cost is `tokens × published price × calls`, where calls are members × rounds. The price in the runner is one
model's published rate, so the column can be checked by hand: five calls of the same council cost five times
one, and a three-round protocol costs fifteen.

### The regression gate

`compareRuns` fails when a mode's acceptance drops further than the two Wilson intervals can explain, and when
mean convergence drops by more than 0.1. With 30 prompts the interval is about ±0.11, which is wide on
purpose: a gate tighter than the sample fails on reshuffling, and the first thing anyone does to a gate that
cries wolf is delete it.

### Replacing the driver with a real model

`scriptedTransport` is one function with one method. A provider-backed `ILLMTransport` drops into the same
`evaluateCouncil` call, and the report — modes, wins, costs, gates — is unchanged. That is the intended next
step and the only part of this page a model key would change.

**Read this first.** The tables below are produced by a scripted transport, not by a model: it answers
from each prompt's own facts with a quality dial, so every number is reproducible with no key and no
spend. They measure the machinery — tally, rounds, cost arithmetic, regression gate — and they say
nothing about how good any model is. Swapping in a provider replaces one function in
`packages/council/src/eval/runner.ts` and the report stays the same shape.

### The golden set

30 decision prompts (operations 7, billing 6, security 6, product 6, engineering 5),
each with the facts a verdict must engage and the tradeoff it must name.
1 of them cannot be answered from the context on purpose, and the judge scores an
unhedged answer to it as dishonest.

| Criterion   | Weight | A 5                                                                                       |
| ----------- | ------ | ----------------------------------------------------------------------------------------- |
| coverage    | 0.30   | Engages every fact that makes this decision hard, not just the first one.                 |
| specificity | 0.20   | Names numbers, components and timeframes rather than saying 'the system' and 'soon'.      |
| tradeoff    | 0.20   | States what the recommendation costs, and what would make the other option right instead. |
| action      | 0.20   | Ends with something the reader can do, or a condition under which to do it.               |
| honesty     | 0.10   | Does not claim more certainty than the context supports.                                  |

### Judge calibration

The judge is a text scorer (see `judge.ts`): it reads coverage of the prompt's facts, numbers, a
concession, a next step and overclaiming. It was calibrated against 53 hand-labelled
verdicts (31 accepted, 22 rejected) written by one annotator — the same person who wrote
the judge, which makes this an upper bound on what a crowd of annotators would show.

| Pass                   | Agreement | Cohen's κ | Accepted by judge | Accepted by label |
| ---------------------- | --------- | --------- | ----------------- | ----------------- |
| Before the review pass | 84.9%     | 0.696     | 27                | 31                |
| After the review pass  | 92.5%     | 0.849     | 27                | 31                |

The review pass changed **four** labels (c12, c24, c30, c36) from accept to reject, and the reason for
each change is recorded in that row's `why`. Those answers were decided without the facts that made the
question hard, and the first labels were too generous; the judge was right and the labels were wrong.
Nothing in the judge changed as a result of reading the disagreements.

Shipping rule: **κ 0.85 — strong agreement on this label set; a release gate would still want a second annotator's labels**. Below κ 0.4 the calibration reports the judge as unusable rather
than publishing a quality number, which is the whole point of measuring it.

Residual disagreements (4):

- `c18` scored 2.6 and was rejected — The opposite decision, argued with the same facts.
- `c33` scored 2.1 and was rejected — Names the exact risk and offers two alternatives.
- `c35` scored 2.5 and was rejected — Decides, uses the audit fact, adds the missing control.
- `c52` scored 2.8 and was rejected — Refuses false precision and gives a range with its basis.

The failure modes are consistent: the judge never accepted an answer a person rejected (0 false
positives in 53), and it under-scores answers whose downside is stated as a consequence of
the choice rather than signalled with "but", whose next step comes before the summary, or which omit a
trivial fact from the prompt (a date) while engaging the substance. Its bias is conservative, so it may
rank and gate regressions but must not be quoted as an absolute quality score.

### Mode comparison

Every mode runs the same 30 prompts through `DeliberationEngine.deliberate` with a
five-member council. "Every member accepted" is the column that discriminates: best-of-five saturates
first, because one strong voice out of five is enough for the council to look good.

| Mode       | Calls | Best verdict accepted (95% CI) | Every member accepted | Convergence ± SE | No majority | Cost / verdict | Latency |
| ---------- | ----- | ------------------------------ | --------------------- | ---------------- | ----------- | -------------- | ------- |
| Standard   | 1 × 5 | 100.0% (88.6%–100.0%)          | 0.0%                  | 76.7% ± 2.7      | 0.0%        | $0.00400       | 4.5 s   |
| Red / blue | 2 × 5 | 100.0% (88.6%–100.0%)          | 63.3%                 | 76.0% ± 2.9      | 0.0%        | $0.00827       | 9.0 s   |
| Socratic   | 3 × 5 | 100.0% (88.6%–100.0%)          | 30.0%                 | 80.0% ± 2.9      | 0.0%        | $0.01213       | 13.5 s  |

Cost uses llama-3.3-70b-versatile at $0.59/M input and $0.79/M
output on the scripted token counts. Rounds multiply the call count, which is why a three-round protocol
costs three times as much for the same council.

### The regression gate, demonstrated

The gate fails when acceptance drops further than the two Wilson intervals can explain. Below is the
same run with the driver's quality dial turned from 0.58 to 0.50 — a stand-in for a prompt change
that makes answers worse:

| Mode     | Metric              | Baseline | Current | Δ      | Noise  | Result   |
| -------- | ------------------- | -------- | ------- | ------ | ------ | -------- |
| standard | accept              | 1.000    | 0.567   | -0.433 | ±0.224 | **fail** |
| standard | everyMemberAccepted | 0.000    | 0.000   | +0.000 | ±0.114 | pass     |
| standard | convergence         | 0.767    | 0.707   | -0.060 | ±0.100 | pass     |
| red_blue | accept              | 1.000    | 1.000   | +0.000 | ±0.114 | pass     |
| red_blue | everyMemberAccepted | 0.633    | 0.000   | -0.633 | ±0.220 | **fail** |
| red_blue | convergence         | 0.760    | 0.760   | +0.000 | ±0.100 | pass     |
| socratic | accept              | 1.000    | 1.000   | +0.000 | ±0.114 | pass     |
| socratic | everyMemberAccepted | 0.300    | 0.000   | -0.300 | ±0.213 | **fail** |
| socratic | convergence         | 0.800    | 0.753   | -0.047 | ±0.100 | pass     |

Convergence and "no majority" are reported with n and an interval (or standard error) because a rate
without one invites reading a five-vote council as a fact. A single prompt's convergence is a fraction
with a denominator of five; only the mean over 30 prompts is worth quoting.

## Reproducing

```bash
pnpm council:evals          # rewrite the block above
pnpm council:evals:check    # fail if it is stale
```

The unit suite pins the parts that must not drift quietly: the golden set's shape, the judge's matching rules
(`8%` is not `18%`, `4,000` is not `400`), the calibration numbers, the vote statistics, the cost arithmetic,
and that a weakened run actually trips the regression gate.

```bash
cd packages/council && npx vp test run src/eval/eval.test.ts
```
